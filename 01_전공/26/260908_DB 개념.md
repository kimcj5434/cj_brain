# DB란 무엇인가: 파일에서 데이터베이스까지

> 대상 독자: 코딩은 할 수 있고 DB를 사용하는 시스템도 쓰지만, DB를 직접 설계하거나 운영해 본 적은 없는 개발자

이 글의 목표는 PostgreSQL 명령을 외우는 것이 아니다. 어떤 서비스가 왜 DB를 두는지, `PostgreSQL`, `Redis`, `MongoDB`, `Elasticsearch` 같은 이름이 문서에 나왔을 때 각각 무엇을 맡는지 읽어 낼 수 있게 되는 것이다.

---

## 0. 가장 짧은 답

**데이터베이스(DB)는 데이터를 오래, 정확하게, 여럿이 함께, 필요한 모양으로 찾고 바꿀 수 있게 관리하는 전문 소프트웨어다.**

프로그램의 메모리에도 데이터를 둘 수 있고, JSON·CSV 파일로 저장할 수도 있다. 그것들은 DB의 경쟁자가 아니라 DB가 등장하기 전의 훌륭한 출발점이다. 다만 데이터·사용자·변경 횟수가 늘면 다음 요구가 동시에 생긴다.

- 프로그램을 껐다 켜도 데이터가 남아야 한다.
- 수백만 건 중 필요한 것만 빨리 찾아야 한다.
- `재고는 0보다 작을 수 없다` 같은 규칙을 항상 지켜야 한다.
- 두 사람이 동시에 바꿔도 한 사람의 변경이 사라지면 안 된다.
- 컴퓨터나 프로세스가 중간에 죽어도, 이미 성공했다고 답한 작업은 잃지 않아야 한다.

DB는 이 문제들을 매번 애플리케이션 코드와 파일 규칙으로 다시 만들지 않도록, 저장·조회·동시성·복구의 약속을 한곳에 모은다.

---

## 1. 메모리와 파일만으로도 시작할 수 있다

### 1.1 실행 중인 메모리

다음은 할 일 앱의 가장 단순한 상태다.

```text
todos = ["DB 개념 정리", "우유 사기"]
```

매우 빠르고 코드도 간단하다. 하지만 프로그램을 종료하면 메모리는 비워진다. 다시 켰을 때 어제의 할 일을 기억해야 한다면 다른 저장 공간이 필요하다.

### 1.2 파일 시스템

`todos.json`에 배열을 저장하면 종료 뒤에도 남는다. 개인 설정, 작은 정적 목록, 빌드 결과물, 한 번 생성하고 거의 읽기만 하는 데이터라면 파일이 가장 단순하고 좋은 선택일 수 있다.

```json
[
  { "id": 1, "title": "DB 개념 정리", "done": false },
  { "id": 2, "title": "우유 사기", "done": true }
]
```

하지만 할 일 앱이 팀 서비스로 자라면 질문이 달라진다.

| 새 요구 | 파일만 쓸 때 직접 해결해야 하는 일 | DB가 제공하려는 것 |
|---|---|---|
| 완료하지 않은 내 할 일만 찾기 | 파일 전체를 읽고 코드로 걸러 냄 | 질의(query), 인덱스 |
| 담당자를 잘못 입력하지 않기 | 모든 프로그램 경로에 검사 코드 작성 | 타입, 제약 조건 |
| 두 명이 동시에 수정 | 파일 덮어쓰기 충돌을 직접 해결 | 트랜잭션, 동시성 제어 |
| 저장 중 프로세스가 종료 | 파일 일부만 써진 상태를 복구 | 로그, 복구 절차 |
| 과거 상태로 되돌리기 | 백업 규칙과 복사본을 직접 관리 | 백업, 복제, 복구 기능 |

핵심은 **파일이 나빠서 DB를 쓰는 것이 아니다. 파일로 직접 관리해야 할 약속이 많아질 때 DB를 쓴다**는 것이다.

## 2. DB가 하는 다섯 가지 일

### 2.1 저장: 껐다 켜도 남게 하기 — 영속성

메모리는 실행 중인 작업대이고, 디스크·SSD·객체 저장소는 오래 보관하는 창고다. DB는 데이터를 창고에 저장하고, 저장 과정이 중간에 실패했을 때도 일관된 상태로 남도록 관리한다.

다만 “DB에 있으니 절대 잃지 않는다”는 뜻은 아니다. 실수로 지운 데이터, 잘못된 애플리케이션 코드, 리전 전체 장애까지 대비하려면 **백업과 복구 계획**도 필요하다.

### 2.2 조회: 필요한 것을 빠르게 찾기 — 질의와 인덱스

쇼핑몰에 상품이 10개라면 전부 훑어도 된다. 1,000만 개라면 `가격이 5만 원 이하이고 재고가 있는 무선 이어폰`을 찾기 위해 전부 읽는 것은 비싸다.

**질의(query)** 는 DB에 하는 질문이다. SQL의 `SELECT`는 대표적인 질의 언어 표현이다. **인덱스(index)** 는 책 뒤의 색인처럼, 데이터 전체를 읽지 않고 후보 위치로 가게 돕는 별도 구조다.

```sql
-- 문법을 외울 필요는 없다. "조건에 맞는 상품을 달라"는 질문이다.
SELECT name, price
FROM products
WHERE category = 'earphone' AND in_stock = true;
```

인덱스는 공짜가 아니다. 상품을 추가·수정·삭제할 때도 색인을 갱신해야 하므로 쓰기 비용과 저장 공간이 든다. 따라서 “인덱스는 많을수록 좋다”가 아니라, **자주 묻는 질문에 맞는 인덱스가 좋다**가 맞다.

#### 한 단계 더: B-tree

PostgreSQL에서 흔히 기본으로 쓰는 B-tree 인덱스는 큰 정렬 목록을 여러 갈림길로 나눈 균형 트리다. 사전에서 `ㅍ`을 찾을 때 처음부터 읽지 않고 중간을 펼치는 것과 비슷하다.

```text
                   [가격 50,000]
                  /             \
       [가격 20,000]             [가격 80,000]
          /       \                 /       \
     ... 12,000  ...            ... 65,000  ...
```

### 2.3 정확성: 말이 되는 데이터만 받기 — 스키마와 제약

**스키마(schema)** 는 데이터의 모양과 규칙이다. 예를 들어 주문에는 주문 번호·주문자·금액이 있어야 하고, 금액은 음수가 아니어야 하며, 주문자는 실제 존재하는 사용자여야 한다.

이런 규칙을 애플리케이션 코드에만 두면, 배치 프로그램·관리자 도구·새 API가 추가될 때마다 빠뜨릴 수 있다. DB의 **제약 조건(constraint)** 은 데이터를 받는 마지막 관문에서 이 규칙을 강제한다.

```text
users                         orders
──────────────                ─────────────────────
id: 42, name: 민지      ←──    user_id: 42, total: 29,000

"user_id: 9999"인 주문은 사용자가 없다면 거절할 수 있다.
```

### 2.4 동시성: 함께 바꾸기 — 트랜잭션

마지막 재고 1개를 A와 B가 동시에 구매한다고 하자. 둘 다 재고를 `1`로 읽고 각각 `0`으로 바꾸면, 주문은 2건인데 재고는 0인 모순이 생길 수 있다.

**트랜잭션(transaction)** 은 여러 변경을 하나의 작업 단위로 묶는 장치다. 주문 생성, 재고 차감, 결제 기록 중 하나라도 실패하면 전부 취소하고, 모두 성공할 때만 확정한다.

```text
재고 확인 → 재고 차감 → 주문 생성 → 결제 기록
                  └──── 하나의 트랜잭션 ────┘

성공: COMMIT (모두 확정)
실패: ROLLBACK (원래대로 되돌림)
```

자주 보는 ACID는 이 약속을 요약한 이름이다.

| 약자 | 뜻 | 주문 사례 |
|---|---|---|
| Atomicity | 전부 성공하거나 전부 실패 | 재고만 줄고 주문은 없는 상태를 막음 |
| Consistency | 정해 둔 규칙을 지킴 | 재고가 음수가 되는 것을 막음 |
| Isolation | 동시에 실행해도 서로의 미완성 작업을 함부로 보지 않음 | 다른 사람의 결제 중간 상태를 보지 않음 |
| Durability | 성공으로 확정한 결과가 장애 뒤에도 남음 | 결제 완료 뒤 서버가 꺼져도 주문을 복구 |

#### 한 단계 더: 락과 MVCC

**락(lock)** 은 특정 데이터나 구조를 동시에 충돌 나게 바꾸지 못하도록 잠시 제어하는 장치다. 하지만 모든 읽기와 쓰기를 한 줄로 세우면 느려진다.

PostgreSQL은 **MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)** 도 사용한다. 쉽게 말해 갱신 중인 행의 새 버전과, 기존 독자가 보던 버전을 함께 관리하여 독자가 미완성 데이터를 보지 않게 한다. 그래서 일반적인 읽기와 쓰기가 불필요하게 서로를 막는 일을 줄인다.

이는 “MVCC면 절대로 대기하지 않는다”는 뜻은 아니다. 같은 행을 동시에 갱신하거나, 더 강한 격리가 필요하면 락·격리 수준·재시도 전략이 여전히 중요하다.

### 2.5 복구: 중간에 꺼져도 약속 지키기 — WAL

DB가 주문을 확정하려는 순간 전원이 나가면 어떻게 될까? 데이터 파일 여기저기를 바로 고치기보다, PostgreSQL 같은 DB는 먼저 **WAL(Write-Ahead Log)** 에 “무슨 변경을 했는지”를 순서대로 기록한다.

```text
변경 요청
  ↓
WAL에 변경 기록을 먼저 안전하게 기록
  ↓
성공 응답(COMMIT)
  ↓
나중에 실제 테이블·인덱스 파일에도 반영
```

장애가 나면 DB는 WAL을 읽어 아직 데이터 파일에 반영하지 못한 확정 변경을 다시 적용할 수 있다. WAL은 중요한 복구 재료지만 **그 자체가 백업과 동의어는 아니다**. 시점 복구(PITR)에는 일반적으로 별도 물리 백업과 보관한 WAL이 함께 필요하다.

## 3. DB 지도: 제품 이름보다 문제와 데이터 모양

DB 계열은 서로 배타적인 상자가 아니다. 제품 하나가 여러 모델이나 기능을 지원하기도 하고, 한 서비스가 여러 DB를 함께 쓰기도 한다. 아래 지도는 “주된 강점”을 잡기 위한 출발점이다.

```text
관계와 정확성 ── PostgreSQL · MySQL · SQLite · Oracle · SQL Server
빠른 상태 접근 ── Redis · DynamoDB
유연한 문서    ── MongoDB · Firestore · Couchbase
대규모 분산 기록 ─ Cassandra · Bigtable · HBase
연결과 경로 탐색 ─ Neo4j · Amazon Neptune
시간순 측정값   ─ InfluxDB · TimescaleDB
텍스트 관련도 검색 ─ Elasticsearch · OpenSearch
```

### 3.1 관계형 DB: 관계와 규칙이 핵심

관계형 DB는 데이터를 행과 열로 된 **테이블**로 표현하고, 테이블 사이의 관계와 규칙을 다룬다. 대표 제품은 PostgreSQL, MySQL, SQLite, Oracle Database, Microsoft SQL Server다.

```text
사용자(users)              주문(orders)
id | name                  id | user_id | total
42 | 민지              ←──  7 | 42      | 29000
```

회원·주문·결제·재고처럼 정확한 규칙, 여러 단계의 변경, 다양한 조건 조회가 중요한 곳에서 좋은 기본 선택이 된다. 관계형 DB는 “엑셀 파일”이 아니다. 제약 조건, 트랜잭션, 인덱스, 질의 최적화가 함께 있는 데이터 관리 시스템이다.

### 3.2 키-값 DB와 캐시: 키로 즉시 꺼내기

키-값 모델은 `키 → 값`으로 데이터를 접근한다.

```text
session:8f9a  →  { user_id: 42, expires_at: ... }
rank:today    →  [42, 18, 71, ...]
```

Redis는 메모리를 적극 활용하는 키-값 DB로, 캐시·세션·랭킹·메시지 처리 등에 널리 쓰인다. DynamoDB는 관리형 분산 서비스이며 키-값과 문서 모델을 함께 지원한다. 

중요한 오해 두 가지:

- Redis는 단지 캐시만은 아니다. 영속화도 지원한다.
- NoSQL은 트랜잭션이나 일관성이 전혀 없다는 뜻이 아니다. 예를 들어 DynamoDB도 트랜잭션과 강한 읽기 일관성 옵션을 제공한다.

다만 어떤 데이터를 서비스의 유일한 “정본(source of truth)”으로 둘지는 제품의 내구성, 메모리 한계, 복구·운영 정책을 포함해 따로 판단해야 한다.

### 3.3 문서형 DB: 함께 변하는 데이터를 한 문서로

문서형 DB는 JSON과 비슷한 중첩 구조의 문서를 자연스럽게 저장한다. MongoDB는 실제로 BSON 형식의 문서를 저장한다.

```json
{
  "user": "민지",
  "shipping_address": { "city": "Seoul" },
  "items": [
    { "name": "이어폰", "qty": 1 },
    { "name": "케이스", "qty": 1 }
  ]
}
```

콘텐츠의 필드가 자주 달라지거나, 한 화면에서 함께 읽고 쓰는 데이터가 중첩될 때 편리하다. 그렇다고 “문서형 DB는 스키마가 전혀 없다”는 뜻은 아니다. 검증 규칙과 인덱스를 둘 수 있고, 데이터 모델을 어떻게 정할지는 여전히 중요하다.

### 3.4 와이드 컬럼·분산 DB: 많은 서버에 나누기

Cassandra, Bigtable, HBase 같은 계열은 매우 큰 규모의 기록을 여러 서버에 나누어 저장하는 데 초점을 둔다. 이때는 조인처럼 자유로운 질문보다, **어떤 키·파티션으로 얼마나 자주 읽고 쓸 것인가**를 먼저 설계하는 일이 중요해진다.

`와이드 컬럼(wide-column)`은 분석 시스템에서 말하는 `columnar storage`와 같은 표현이 아니다. 전자는 희소한 행·열 구조와 분산 접근 모델을 가리키는 경우가 많다.

### 3.5 그래프 DB: 연결 자체가 질문일 때

그래프 DB는 노드(node), 관계(relationship), 속성(property)을 중심으로 모델링한다.

```text
(민지)-[:FOLLOWS]->(준호)-[:WORKS_AT]->(회사 A)
```

친구 추천, 권한 상속, 사기 탐지처럼 “몇 단계 건너 어떤 관계가 있는가?”가 주된 질문이면 Neo4j나 Amazon Neptune 같은 그래프 DB가 후보가 된다. 관계형 DB의 JOIN을 무조건 대체하는 도구는 아니다.

### 3.6 시계열 DB: 시간 축이 중심일 때

서버 CPU, IoT 센서, 주가처럼 시간 순서로 계속 들어오는 측정값은 시계열 데이터다.

```text
10:00  CPU 31%
10:01  CPU 45%
10:02  CPU 92%  ← 언제부터 이상했는가?
```

InfluxDB, TimescaleDB 같은 제품은 시간 범위 조회, 시간 단위 집계, 오래된 데이터 보관 정책에 강점을 둔다. 단순히 `created_at` 열이 있다는 이유만으로 시계열 DB가 필요한 것은 아니다.

### 3.7 검색 엔진: 단어와 관련도 순서로 찾기

`"무선 이어폰"`을 검색할 때는 정확히 같은 문자열뿐 아니라 형태가 비슷한 단어, 단어의 중요도, 관련도 순서가 필요하다. Elasticsearch와 OpenSearch는 이러한 전문 검색과 로그 분석에 특화된 엔진이다.

```text
검색어: "노이즈 캔슬링 이어폰"
       ↓
관련도 순 결과: 상품 A, 리뷰 B, 상품 C ...
```

검색 엔진은 대개 주문·결제의 최종 원장을 대체하기보다, 원장 DB의 데이터를 색인해 빠른 검색 화면을 제공하는 역할로 함께 쓰인다.

---

## 4. 한 서비스에는 DB가 여러 개일 수 있다

현실의 서비스는 하나의 제품을 고르는 시험 문제가 아니다. 데이터의 성격에 따라 책임을 나눌 수 있다.

```text
                 ┌─ PostgreSQL: 주문·결제·재고의 정본과 규칙
쇼핑몰 API ──────┼─ Redis: 로그인 세션·자주 보는 상품 캐시
                 └─ Elasticsearch: 상품명·설명 검색
```

이 구조에서 Redis나 Elasticsearch가 없어도 서비스는 처음엔 동작할 수 있다. 트래픽과 검색 요구가 커질 때 추가한다. 반대로 처음부터 세 종류를 넣으면 동기화와 운영 복잡도도 함께 늘어난다. **가장 단순하게 시작하되, 실제 병목과 요구가 생길 때 역할을 분리하는 것**이 좋은 기본 전략이다.

## 5. PostgreSQL을 읽는 최소 언어

PostgreSQL은 관계형 DBMS 중 하나다. 여기서는 SQL 문법을 배우기보다, 제품 문서에 나오는 핵심 단어를 읽는 법을 정리한다.

| 단어 | 한 줄 이해 | 왜 알아야 하나 |
|---|---|---|
| 테이블 | 같은 종류의 사실을 모은 표 | 데이터 모델의 기본 단위 |
| 행(row) | 한 개체에 대한 한 기록 | 사용자 한 명, 주문 한 건 |
| 열(column) | 기록의 한 속성 | `email`, `created_at`, `price` |
| 기본 키(primary key) | 행을 유일하게 가리키는 값 | 같은 이름의 사용자도 구분 |
| 외래 키(foreign key) | 다른 테이블의 행을 가리키는 값 | 주문과 사용자를 연결 |
| SQL | DB에 질문·변경을 요청하는 언어 | 읽기와 쓰기의 공통 인터페이스 |
| 인덱스 | 빠른 탐색을 위한 보조 구조 | 조회 비용과 쓰기 비용을 함께 좌우 |
| 트랜잭션 | 전부 성공 또는 전부 취소되는 작업 묶음 | 여러 변경의 정확성 보장 |

### 아주 작은 관찰 예시

```sql
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 10 AND stock > 0;
INSERT INTO orders (product_id, user_id) VALUES (10, 42);
COMMIT;
```

이 코드에서 중요한 것은 문법보다 경계다. `BEGIN`부터 `COMMIT`까지를 하나의 약속으로 묶으려는 의도다. 실제 서비스에서는 재고 차감 성공 여부 확인, 오류 처리, 격리 수준, 재시도까지 설계해야 한다.

## 6. 사례: lakeFS에서 PostgreSQL은 무엇을 맡는가

lakeFS는 데이터 레이크의 데이터에 Git과 비슷한 버전 관리 경험을 제공하는 시스템이다. PostgreSQL을 사용하는 lakeFS 구성이라면, PostgreSQL을 “CSV·Parquet 파일의 실제 바이트를 보관하는 창고”로 이해하면 안 된다.

```text
사용자·파이프라인
        ↓
      lakeFS
   ┌────┴──────────────────┐
   │                       │
객체 저장소                PostgreSQL (한 구성 예)
S3·GCS·Azure Blob          브랜치·권한·변경 중인 객체의
실제 파일/객체 바이트       메타데이터와 조정 상태
```

즉 객체 저장소는 큰 데이터 파일을 맡고, DB는 "어느 브랜치가 무엇을 가리키는가", "누가 어떤 권한을 갖는가", "아직 커밋되지 않은 변경은 무엇인가"처럼 빠르게 조회·일관되게 갱신해야 할 상태를 맡는다. 이것은 앞에서 본 **파일/객체 저장소와 DB의 역할 분리**의 실제 사례다.

주의할 점도 있다. lakeFS의 현재 설정은 PostgreSQL만 강제하지 않으며, 구성에 따라 다른 키-값 메타데이터 저장소를 선택할 수 있다. 따라서 정확한 표현은 “lakeFS는 항상 PostgreSQL을 쓴다”가 아니라 **“PostgreSQL을 백엔드로 구성한 lakeFS에서는 …”** 이다.

## 7. DB를 써야 할 때와 굳이 쓰지 않아도 될 때

### DB가 특히 유용한 신호

- 여러 사용자나 여러 프로세스가 같은 데이터를 읽고 바꾼다.
- 검색·정렬·집계 조건이 늘고 데이터가 커진다.
- 데이터 규칙을 한곳에서 강제해야 한다.
- 여러 변경이 함께 성공하거나 실패해야 한다.
- 장애 복구, 권한, 백업, 복제가 필요하다.

### 파일 또는 단순 저장이 더 좋은 신호

- 개인용 설정처럼 작고, 한 프로그램만 쓰며, 동시에 수정하지 않는다.
- 정적 사이트의 콘텐츠처럼 생성 뒤 거의 읽기만 한다.
- 일회성 스크립트의 중간 결과이며 복잡한 조회가 필요 없다.
- DB 서버를 운영하는 비용이 얻는 이점보다 크다.

처음부터 “DB를 쓸까?”보다 다음 질문을 하면 선택이 쉬워진다.

1. 데이터는 누가 동시에 바꾸는가?
2. 어떤 질문을 얼마나 자주, 얼마나 빨리 해야 하는가?
3. 틀리거나 사라졌을 때의 비용은 얼마인가?
4. 데이터의 모양은 안정적인가, 자주 달라지는가?
5. 운영할 사람과 비용은 있는가?

답이 단순하면 파일·SQLite·관리형 DB처럼 단순한 선택에서 시작할 수 있다. 요구가 복잡해질수록 PostgreSQL 같은 관계형 DB 또는 특화 저장소를 검토한다.

## 8. 발전 흐름: 왜 여러 DB가 생겼나

```text
파일에 직접 저장
  ↓  데이터 공유·검색·규칙·복구 요구 증가
관계형 DB와 SQL
  ↓  웹 규모 확대, 데이터 형태·접근 패턴의 다양화
키-값 · 문서형 · 분산형 · 그래프 · 시계열 · 검색 엔진
  ↓  오늘
한 제품이 모든 문제를 푸는 것이 아니라, 요구에 맞춰 조합
```

관계형 DB가 오래되고 보편적인 이유는 정확성과 범용 질의에 강하기 때문이다. NoSQL 계열이 등장한 이유는 관계형 DB가 쓸모없어서가 아니라, 아주 빠른 키 조회, 유연한 문서, 대규모 분산 기록, 그래프 탐색, 시계열 집계, 전문 검색처럼 다른 우선순위가 생겼기 때문이다.

따라서 "SQL 대 NoSQL"은 좋은 대립이 아니다. 더 좋은 질문은 **“내 데이터의 모양, 가장 중요한 질문, 정확성 요구, 운영 제약은 무엇인가?”** 이다.

## 부록 A. 용어 설명집

| 용어 | 쉬운 설명 | 함께 볼 용어 |
|---|---|---|
| ACID | 트랜잭션이 지키려는 네 가지 약속의 약자 | 트랜잭션, 격리성 |
| B-tree | 정렬된 값을 빠르게 찾는 균형 잡힌 트리형 인덱스 | 인덱스 |
| DBMS | DB를 저장·조회·관리하는 소프트웨어. PostgreSQL 등이 이에 해당 | DB |
| MVCC | 여러 버전의 데이터를 관리해 동시 읽기·쓰기를 조정하는 방식 | 트랜잭션, 락 |
| NoSQL | 하나의 엄격한 기술 분류가 아니라, 전통적 관계형 모델 밖의 여러 DB 계열을 부르는 넓은 말 | 문서형, 키-값 |
| WAL | 실제 데이터 파일보다 변경 기록을 먼저 남겨 장애 복구를 돕는 로그 | 복구, 트랜잭션 |
| 객체 저장소 | 파일을 객체 단위로 대규모 보관하는 저장소. S3 등이 대표적 | 메타데이터 |
| 격리 수준 | 동시에 실행되는 트랜잭션이 서로의 변경을 어디까지 볼지 정하는 규칙 | MVCC, 락 |
| 기본 키 | 테이블의 각 행을 유일하게 구분하는 열 또는 열 조합 | 외래 키 |
| 메타데이터 | 데이터 자체를 설명하는 데이터. 파일 크기·위치·생성 시각 등이 예 | 객체 저장소 |
| 복제(replication) | 데이터를 다른 서버에도 복사해 가용성·읽기 성능 등을 높이는 방식 | 백업 |
| 백업 | 실수·장애 뒤 되돌리기 위해 보관하는 복사본 | WAL, 복구 |
| 샤딩(sharding) | 큰 데이터를 여러 서버에 나누어 저장하는 방식 | 분산 DB |
| 스키마 | 데이터의 구조와 규칙에 대한 약속 | 제약 조건 |
| 인덱스 | 특정 조건의 데이터를 빠르게 찾기 위한 보조 구조 | B-tree |
| 정본(source of truth) | 어떤 사실의 최종적으로 믿을 수 있는 원천 데이터 | 캐시 |
| 제약 조건 | 잘못된 데이터가 들어오지 못하게 하는 DB 규칙 | 스키마, 무결성 |
| 질의(query) | DB에 데이터를 찾아 달라거나 집계해 달라고 하는 요청 | SQL |
| 캐시 | 원본보다 빠르게 다시 쓰기 위해 임시로 둔 데이터 | Redis, 정본 |
| 트랜잭션 | 여러 변경을 전부 확정하거나 전부 취소하는 작업 단위 | ACID, COMMIT |
| 외래 키 | 다른 테이블의 기본 키를 참조해 관계를 표현하는 열 | 기본 키, 무결성 |
