# AI 활용 딥러닝 모델 개발 Research Workflow (v1)

세 논문에서 차용한 요소를 재조합해 **"AI를 연구 조수로 쓰는 딥러닝 모델 개발"** 전용 워크플로우로 재정의한 문서.

- 근거 논문: [AI4Research Survey](https://arxiv.org/abs/2507.01903v1) · [Rethinking the AI Scientist](https://arxiv.org/abs/2601.12542) · [Deep Research Survey](https://arxiv.org/abs/2506.12594)
- 대상: 딥러닝 모델을 새로 만들거나 개선하는 리서치 (논문 재현, 아키텍처 개선, 학습 기법 탐색, 도메인 적용)

---

## 0. 설계 원칙 — 세 논문에서 무엇을 가져왔는가

| 원칙 | 출처 | 내용 |
|---|---|---|
| **P1. 상태를 파일로 외재화** | 논문2 world state, 논문3 memory | 컨텍스트를 프롬프트가 아니라 저장소에 둔다 |
| **P2. 자동화 수준을 단계별로 다르게** | 논문1 semi ↔ full automatic | 모든 단계를 같은 수준으로 자동화하지 않는다 |
| **P3. 실험 전에 예측한다** | 논문1 Pre-Experiment Estimation | 자원 투입 전 프록시로 기대효과 추정 후 컷 |
| **P4. 3축 분리 평가** | 논문1 Novelty/Validity/Significance | "새로운가·맞는가·중요한가"를 섞지 않는다 |
| **P5. Close-loop** | 논문1 experiment management | 실험을 던져놓지 않고 중간 결과로 계획 수정 |
| **P6. 빠른 사이클 + 병렬** | 논문2 4단계 파이프라인 | 문헌 조사와 데이터/코드 분석을 동시에 시작 |
| **P7. 비판을 별도 단계·별도 역할로** | 논문2 critical reflection, 논문3 validator | 실행한 주체가 자기 결과를 검증하지 않는다 |
| **P8. 이벤트 기반 human checkpoint** | 논문2 semi-autonomous mode | 모순·모호성이 트리거. 시간이 트리거가 아니다 |
| **P9. 품질 임계치 게이트** | 논문3 §2.3.2 | 수치 기준을 못 넘으면 다음 단계 진입 금지 |
| **P10. 모든 주장에 출처** | 논문2 DOI, 논문3 source grounding | 논문 링크·커밋 해시·로그 ID를 첨부 |
| **P11. 한계 자기신고** | 논문2, 논문3 | 산출물에 "검증하지 않은 것"을 반드시 포함 |

**핵심 재정의**: 논문2는 "분 단위 사이클"을 무기로 삼았지만 딥러닝 학습은 시간~일 단위다. 따라서 이 워크플로우는 **속도를 이원화**한다.

> **Fast Loop** (분~시간): 문헌·설계·프록시 실험·분석 — AI가 주도
> **Slow Loop** (시간~일): 본 학습·대규모 스윕 — 사람이 승인하고 AI가 모니터링

## 1. 전체 구조

```
                    ┌───────────────────────────────────────┐
                    │      RESEARCH STATE (파일 저장소)      │
                    │  objectives · hypotheses · findings    │
                    │  methods · insights · datasets         │
                    │  + tried[] · rejected[] · open_qs[]    │
                    └────────────┬──────────────────────────┘
                                 │ 모든 단계가 read/write
   ┌──────────────────────────────┴──────────────────────────────┐
   │                                                              │
 P0 문제 정의 ─▶ P1 지형 파악 ─▶ P2 가설 설계 ─▶ P3 베이스라인
                  (병렬: 문헌 ∥ 데이터/코드)         │ GATE-B
                                                     ▼
                          P4 프록시 실험 (Fast Loop, 반복) ◀─┐
                                    │ GATE-P                  │
                                    ▼                         │
                          P5 본 실험 (Slow Loop) ─────────────┤ close-loop
                                    │ GATE-V                  │
                                    ▼                         │
                          P6 검증·해석 (독립 validator) ──────┘
                                    │
                                    ▼
                          P7 문서화·핸드오프
```

## 2. Research State — 상태 스키마

리포지토리 루트에 `research/` 디렉터리를 두고 아래를 유지한다. **AI 세션은 시작할 때 이 파일들을 읽고, 끝날 때 갱신한다.**

```
research/
  STATE.md            # 현재 상태 요약 (아래 스키마). 항상 1~2페이지 이내로 유지
  hypotheses.md       # 가설 대장: ID, 서술, 근거, 예측, 상태(open/testing/confirmed/rejected)
  experiments.md      # 실험 대장: ID, 가설ID, 설정, 결과, 커밋해시, 로그경로, 판정
  findings.md         # 확정된 발견 (재현된 것만)
  rejected.md         # 폐기된 아이디어 + 폐기 이유  ← AI가 같은 제안 반복하는 것 방지
  literature.md       # 조사한 논문: 링크, 핵심 주장, 우리 문제와의 관계, 신규성 라벨
  decisions.md        # 결정 로그: 무엇을, 왜, 어떤 근거로 (reasoning trail)
  open_questions.md   # 미해결 질문
```

`STATE.md` 스키마 (논문2의 6슬롯 + 3슬롯 확장):

```markdown
## Objectives      최종 목표 + 성공 기준(수치)
## Hypotheses      현재 검증 중인 가설 (ID, 한 줄)
## Findings        재현된 사실만
## Methods         현재 확정된 실험 프로토콜 (데이터 split, 지표, seed 정책)
## Insights        아직 확정 아니지만 유력한 직관
## Datasets        사용 데이터, 버전, 라이선스, 알려진 문제
## Tried           이미 시도한 설정 (중복 방지)
## Rejected        폐기 목록 + 이유
## Open Questions  미해결
```

### 메모리 계층 (논문3 §2.1.2 차용)

| 계층 | 내용 | 수명 | AI에 주입하는 방식 |
|---|---|---|---|
| Working | 현재 실험 1개의 로그·코드 | 세션 | 원문 그대로 |
| Episodic | 실험 대장, 최근 10개 실험 요약 | 프로젝트 | 요약 테이블 |
| Semantic | findings / rejected / literature | 영구 | 관련된 항목만 선별 주입 |

**규칙**: raw 로그를 프롬프트에 통째로 붙이지 않는다. `실험별 요약 → 스윕 요약 → 프로젝트 인사이트`로 3단 압축한 것을 넣는다.

## 3. 에이전트/역할 구성

논문3의 4역할 + 논문2의 4에이전트를 딥러닝용으로 재편. **한 세션이 여러 역할을 겸하지 않는다** (특히 Builder와 Validator).

| 역할 | 담당 | 자동화 수준 |
|---|---|---|
| **Coordinator** (사람) | 목표 설정, 게이트 통과 승인, 자원 배분 | 수동 |
| **Scout** | 문헌 검색, 선행연구 정리, 신규성 라벨링 | 완전 자동 |
| **Diagnostician** | 데이터 진단, 기존 코드 분석, 베이스라인 재현 | 반자동 |
| **Designer** | 가설 형식화, 실험 설계, 스윕 계획 | 반자동 (사람 승인 필수) |
| **Builder** | 코드 구현, 실험 실행, 에러 복구 | 완전 자동 |
| **Validator** | 결과 검증, 반박 시도, leakage/버그 탐지 | 완전 자동 (**Builder와 분리**) |
| **Scribe** | 리포트·문서 생성, 결정 로그 정리 | 완전 자동 |

**Builder 루프** (논문2 Data Analysis Agent의 6노드 차용):
`plan → generate → execute → observe → reflect → answer`
observe/reflect를 생략하면 에러 루프에 빠진다. 실행 후 반드시 "무엇이 나왔는지 관찰"과 "왜 그런지 성찰"을 분리 출력하게 한다.

## 4. 단계별 워크플로우

각 단계는 **목적 / AI 활용 / 지켜야 할 규칙 / 통과 게이트 / 금지사항**으로 규정한다.

---

### P0. 문제 정의 (Problem Framing)
**목적**: 무엇을 개선하려는지, 성공을 무엇으로 판정할지 확정.

**AI 활용**
- 문제 서술을 주고 "이 문제를 측정 가능한 형태로 다시 써봐. 지표 후보 3개와 각 지표의 실패 모드"를 요청
- 성공 기준의 반례 생성: "이 지표가 올라가도 실제로는 나빠지는 경우"

**규칙**
- 성공 기준은 **수치 + 데이터셋 + 지표 + 허용 비용**으로 쓴다. ("정확도 향상" ✗ → "ImageNet-1k top-1, 동일 FLOPs에서 +0.5%p, 학습 예산 200 GPU-hr 이내" ○)
- **Significance를 먼저 쓴다** (논문1 P4). "이게 되면 무엇이 달라지는가"를 한 문장.
- 실패 판정 기준도 함께 쓴다 (kill criteria).

**GATE-0**: 성공 기준·실패 기준·예산이 수치로 적혔는가.

**금지**: AI에게 문제 정의를 위임하지 않는다. AI는 문제를 날카롭게 다듬는 데만 쓴다.

---

### P1. 지형 파악 (Landscape) — **병렬 실행**
**목적**: 선행연구와 우리 자산(데이터·코드)의 현재 상태를 동시에 파악.

**AI 활용 — 두 트랙을 동시에 띄운다** (논문2 §2단계 차용)
- **Track A (Scout)**: 문헌 검색. 쿼리를 3~5개로 분해 → 검색 → re-rank → 요약. 각 논문에 대해 `링크 / 핵심 주장 / 우리 문제와의 관계 / 사용 가능한 코드 여부`를 표로.
- **Track B (Diagnostician)**: 데이터 통계, 라벨 분포, 중복·누수 후보, 기존 코드의 학습 파이프라인 요약, 병목 프로파일.

**규칙**
- 문헌은 **Novelty 5등급 라벨**을 붙인다 (논문2 차용): `identical / subset / superset / near-miss / novel`
  - identical → 우리 아이디어 폐기 또는 재현 연구로 전환
  - subset → 우리가 더 일반적, 논문화 각도 확보
  - superset → 이미 더 일반적인 결과 있음, 차별점 필수
  - near-miss → **가장 가치 있는 영역.** 차이를 명문화
- **모든 요약에 출처 링크 필수** (P10). 링크 없는 주장은 삭제한다.
- AI가 존재하지 않는 논문을 인용할 수 있다. **인용된 논문은 실제 존재 여부를 반드시 확인**한다 (제목+저자 검색).
- 오픈액세스만 검색하면 문헌의 절반을 놓친다 (논문2 한계). 사내 라이브러리/구독 저널을 별도로 확인.

**GATE-1**: 관련 논문 ≥N개 정리 + 그중 near-miss/identical 판정 완료 + 데이터 누수 후보 점검 완료.

**금지**: 문헌 조사가 끝날 때까지 데이터 분석을 미루는 것 (직렬화 = 사이클 2배).

---

### P2. 가설 설계 (Hypothesis Formalization)
**목적**: "왜 이게 통할 것인가"를 검증 가능한 명제로 만든다.

**AI 활용**
- 아이디어 생성: 3개 소스를 모두 쓴다 (논문1 §5.1)
  - *Internal*: "이 문제에 대해 알려진 접근 10개를 나열하고 조합해봐"
  - *External knowledge*: P1의 문헌에서 전이 가능한 기법 추출
  - *External feedback*: **P1 데이터 진단 결과에서 직접 유도** (예: 롱테일 분포 발견 → 리밸런싱 가설)
- 형식화 (논문1 §5.3.1): 각 가설을 아래 템플릿으로 강제
  ```
  H-<id>
  주장: <변경 X를 하면 지표 M이 개선된다>
  메커니즘: <왜. 수식/가정 수준으로>
  예측: <성공 시 관측될 구체적 신호. 실패 시 신호도 함께>
  반증 조건: <이 결과가 나오면 가설은 틀림>
  선행연구 관계: <novelty 라벨 + 근거>
  예상 비용: <GPU-hr>
  ```
- 아이디어 다양화: 서로 다른 관점의 세션 3개를 독립적으로 돌려 아이디어를 뽑고, 그다음 합친다. 한 세션에서 10개 뽑으면 서로 비슷한 것만 나온다.

**규칙 — 3축 게이트** (논문1 P4). 각 가설을 **따로따로** 판정:
| 축 | 질문 | 판정자 |
|---|---|---|
| Novelty | 이미 있는가? | Scout (문헌 대조) |
| Validity | 메커니즘이 성립하는가? | Designer + Validator |
| Significance | 되면 무엇이 달라지는가? | 사람 (Coordinator) |

- 세 축 중 하나라도 명확히 실패하면 즉시 폐기 → `rejected.md`에 **이유와 함께** 기록
- **반증 조건이 없는 가설은 실험하지 않는다.** 반증 불가능한 가설은 무한히 "조금 더 튜닝하면 될 것 같다"로 이어진다.

**GATE-2**: 가설 3~7개가 템플릿으로 형식화 + 3축 판정 완료 + 우선순위 부여.

**금지**: AI가 제안한 아이디어를 근거 확인 없이 채택. AI는 그럴듯한 메커니즘 설명을 항상 만들어낸다.

---

### P3. 베이스라인 고정 (Baseline Lock)
**목적**: 비교 기준을 재현하고 못 박는다. **이 단계를 건너뛰면 이후 모든 결과가 무의미하다.**

**AI 활용**
- 원저자 코드/설정 대조, 하이퍼파라미터 표 추출
- 데이터 split·전처리·평가 코드 리뷰 (leakage 탐지 프롬프트)
- 재현 실패 시 차이점 후보 나열

**규칙**
- 베이스라인은 **논문 수치와 오차 범위 내로 재현**되어야 한다. 못 하면 원인을 문서화하고, 우리 재현치를 공식 기준으로 선언한다.
- **seed 정책 확정**: 최소 3 seed, 평균±표준편차 보고. 이후 모든 실험에 동일 적용.
- 평가 코드를 동결(freeze)하고 커밋 해시를 `STATE.md`에 기록. 이후 평가 코드 변경 시 전 실험 재평가.
- **결정론성 확보**: 데이터 순서, augmentation seed, cuDNN 설정 고정.

**GATE-B (강한 게이트)**
- [ ] 베이스라인 재현 오차 < 사전 정의 임계치
- [ ] 3 seed 분산 측정 완료 → **이 분산보다 작은 개선은 이후 "개선"으로 인정하지 않는다**
- [ ] leakage 점검 통과 (train/val/test 중복, 시간 누수, 정규화 통계 누수)
- [ ] 평가 코드 동결 + 커밋 해시 기록

**금지**: 베이스라인 없이 "새 모델이 좋다"를 판정. seed 1개 결과로 비교.

---

### P4. 프록시 실험 (Fast Loop) — 반복 구간
**목적**: 값싼 실험으로 가설을 걸러낸다. 논문1의 **Pre-Experiment Estimation**을 이 워크플로우의 중심 장치로 승격.

**프록시 설계** (본 실험의 1/10~1/100 비용)
- 작은 모델 / 짧은 스텝 / 데이터 서브셋 / 낮은 해상도 / 짧은 시퀀스
- **프록시의 타당성을 먼저 검증한다**: 베이스라인과 알려진 개선 1개를 프록시에서 돌려, 순위가 본 실험과 일치하는지 확인. 순위가 뒤집히는 프록시는 쓰지 않는다.

**AI 활용 (여기가 AI 효율의 핵심 구간)**
- Builder에게 실험 코드 생성/실행을 완전 자동 위임. 단 `plan→generate→execute→observe→reflect→answer` 루프를 강제.
- 여러 가설을 **독립 세션으로 병렬 실행**. 가설 간 코드 충돌이 있으면 브랜치/워크트리 분리.
- 실패 로그 자동 분류: OOM / NaN / 수렴 실패 / 데이터 에러 / 설정 오류
- 매 실험 후 `experiments.md` 자동 갱신 (ID, 설정 diff, 결과, 커밋, 로그 경로)

**규칙**
- **한 실험은 한 변수만 바꾼다.** AI가 "이것도 같이 개선했습니다"를 하면 실험이 무효가 된다. 프롬프트에 명시적으로 금지.
- 실험 실행 전에 **예상 결과를 먼저 적는다** (사전 등록, pre-registration). 결과를 본 뒤 해석을 맞추는 것을 막는다.
- **Close-loop** (논문1 P5): 매 사이클 종료 시 Designer가 남은 스윕 계획을 재수립. 초기 계획을 끝까지 고수하지 않는다.
- 비용 상한을 실험당·사이클당 설정. 초과 시 자동 중단 → human checkpoint.
- 중복 방지: 실행 전 `Tried` 목록 조회. AI에게 항상 `tried.md`를 주입한다.

**GATE-P**: 프록시에서 baseline 대비 개선이 **seed 분산의 2배 이상**인 가설만 P5로 승격. 그 외는 rejected 또는 재설계.

**금지**
- 프록시 결과를 최종 결과로 보고
- 타당성 미검증 프록시 사용
- 여러 변경을 한 번에 넣고 "합쳐서 좋아졌다"로 결론

---

### P5. 본 실험 (Slow Loop)
**목적**: 승격된 가설을 실제 규모에서 검증.

**AI 활용**
- 스윕 설정 생성, 자원 스케줄링, 학습 모니터링(발산·정체 탐지 → 알림)
- 학습 중 중간 로그 해석 리포트 자동 생성 (사람이 로그를 직접 보는 시간을 줄인다)
- **자동 조기 중단 제안** — 실행은 사람 승인

**규칙**
- 본 실험 착수는 **사람 승인 필수** (비용이 크다). 승인 시 `decisions.md`에 근거 기록.
- Open-loop / Close-loop를 명시 선택 (논문1 §5.4.3): 재현 목적이면 open-loop(설정 고정), 탐색 목적이면 close-loop(중간 조정 허용). **섞으면 결과 해석이 불가능해진다.**
- 최소 3 seed. 동일 예산(FLOPs/시간)에서 비교 — 학습 시간이 더 길어서 좋아진 것을 개선으로 착각하지 않는다.
- ablation을 본 실험과 **같은 배치로 계획**한다. 나중에 하면 안 한다.

**GATE-V**: 개선이 3 seed 신뢰구간에서 유의미 + 동일 예산 비교 + ablation 완료.

**금지**: 스윕에서 가장 좋은 하나를 골라 baseline의 단일 설정과 비교 (베이스라인도 동일 예산으로 튜닝해야 한다).

---

### P6. 검증·해석 (Independent Validation) — **별도 세션**
**목적**: 결과를 깨뜨려 본다. 논문2의 critical reflection + 논문3의 validator를 결합.

**AI 활용 — Validator 세션은 Builder와 완전히 분리한다.** 컨텍스트를 공유하지 않고, 결과와 코드만 주고 다음을 지시:
1. **반박 프롬프트**: "이 결론이 틀렸다고 가정하고, 가능한 원인을 찾아라. 기본값은 '틀렸다'로 둔다."
2. **Leakage/버그 감사**: split, 정규화 통계, 라벨 사용, 평가 지표 구현, 테스트셋 반복 사용(다중 비교) 점검
3. **Theoretical Consistency Analysis** (논문1 §5.4.5): "P2에서 예측한 메커니즘 신호가 실제로 관측되는가?" — 지표는 올랐지만 예측한 중간 신호(예: attention 분포 변화, gradient norm)가 없으면 **다른 이유로 좋아진 것**이다.
4. **대안 설명 3개 생성**: 우리 가설 외에 이 결과를 설명할 수 있는 가설 3개와 각각을 배제할 실험

**규칙**
- 서로 다른 관점의 validator를 복수로 돌린다 (correctness / leakage / 재현성 / 통계). 동일 프롬프트 3번보다 관점 3개가 낫다.
- **Validator 다수가 반박하면 결론을 내리지 않는다.** 추가 실험으로 넘긴다.
- 실패·이상 결과에서 post-hoc 가설을 추출해 `open_questions.md`로 (논문1 Exploratory Analysis). 실패는 폐기물이 아니라 P2의 입력이다.

**GATE-6**: 독립 재현 1회 성공 + leakage 감사 통과 + 메커니즘 신호 확인 또는 "다른 이유"의 규명.

**금지**: 실험을 수행한 AI 세션에 검증을 맡기는 것. 자기 검증은 통과율이 비정상적으로 높다.

---

### P7. 문서화·핸드오프
**목적**: 재현 가능한 산출물로 만든다.

**AI 활용**
- `STATE.md` + `experiments.md`에서 리포트 자동 생성 (논문2의 문서 자동 생성 차용)
- 표·그림 생성, 문헌 인용 정리, 초안 작성

**산출물 규격 (필수 항목)**
1. 주장 목록 — 각 주장에 **증거 링크**(실험 ID → 커밋 해시 → 로그 경로 → 논문 DOI)
2. 재현 명령어 + 환경 + 데이터 버전
3. ablation 표
4. seed 분산·신뢰구간
5. **Limitations 섹션 — "검증하지 않은 것" 명시** (P11). 논문2·3 모두 이걸 명시적 규범으로 삼는다.
6. Decision log — 주요 갈림길에서 왜 그 선택을 했는지
7. Negative results — 폐기된 가설과 이유

**규칙**: AI가 작성한 문장 중 **수치와 인용은 전수 확인**한다. 이 두 가지가 AI 문서 생성의 주요 오류원이다.

## 5. Human Checkpoint 규칙 (이벤트 트리거)

논문2의 semi-autonomous mode를 차용. **시간 기반이 아니라 이벤트 기반**으로 AI를 멈춘다. 아래가 발생하면 AI는 진행을 멈추고 사람에게 보고한다.

| 트리거 | 이유 |
|---|---|
| 결과가 이전 findings와 **모순** | 둘 중 하나가 틀렸다. 진행하면 오류가 전파된다 |
| 지표 간 **불일치** (loss↓ 인데 target 지표↓) | 지표/평가 구현 문제 가능성 |
| **비용 임계 초과** (실험당/사이클당 예산) | 자원 폭주 방지 |
| 계획에 없던 **설계 선택**이 필요 | 근거 없는 임의 선택 방지 |
| 베이스라인이 **재현되지 않음** | 그 위의 모든 실험이 무효 |
| 개선폭이 **비정상적으로 큼** (>기존 SOTA 대비 과도) | 거의 항상 leakage나 버그 |
| 문헌 판정이 **identical** | 연구 방향 재설정 필요 |
| AI가 **같은 에러를 3회 반복** | 접근 자체가 잘못됨 |

**완전 자율로 돌려도 되는 구간**: P1 문헌 조사, P3 재현 시도, P4 프록시 실험 실행, P6 감사, P7 초안 작성.
**반드시 사람이 승인하는 구간**: P0 문제 정의, GATE-2 가설 채택, P5 본 실험 착수, 최종 결론.

## 6. AI 성능 극대화 기법

### 6.1 컨텍스트 엔지니어링 (효과가 가장 큰 항목)
- **압축 계층 유지**: raw 로그 → 실험 요약 → 스윕 요약 → 인사이트. AI에는 상위 2단만 준다.
- **관련성 선별 주입** (논문3 relevance-ranked): 현재 질문과 관련된 findings/rejected만 넣는다. 전체를 붓지 않는다.
- **`rejected.md`를 항상 주입**: AI가 이미 폐기한 아이디어를 반복 제안하는 것을 막는 가장 값싼 방법.
- **세션 분할**: 문헌 조사 세션, 구현 세션, 검증 세션을 분리. 한 세션에 다 넣으면 후반 품질이 급락한다.
- **STATE.md는 2페이지 이내로 유지.** 길어지면 요약을 다시 압축한다.

### 6.2 역할 분리와 다양성
- **Builder ≠ Validator** (가장 중요한 규칙). 컨텍스트를 공유하지 않는다.
- **동일 프롬프트 N회 < 관점 N개.** 검증은 correctness / leakage / 통계 / 재현성 같은 서로 다른 렌즈로.
- 아이디어 생성은 독립 세션 3개 → 그 후 합치기. 한 세션 내 10개 요청은 다양성이 낮다.

### 6.3 출력 규격화
- 자유 서술 대신 **고정 스키마**를 요구한다 (가설 템플릿, 실험 레코드, 검증 리포트).
- 스키마는 파싱 가능한 형태로 → 다음 단계 자동화가 가능해진다.
- "확신도"와 "근거 강도"를 별도 필드로 요구. 근거 없는 확신을 눈에 보이게 만든다.

### 6.4 검증 자동화 (hallucination 대응, 논문3)
- **Source grounding**: 모든 수치는 로그 경로, 모든 인용은 링크. 없으면 그 문장을 삭제.
- **Contradiction detection**: 새 결론을 `findings.md`와 자동 대조. 모순 시 플래그.
- 인용 논문의 **존재 여부 실검증** (제목+저자 검색). AI는 그럴듯한 가짜 인용을 만든다.

### 6.5 비용 효율
- 값싼 작업(로그 파싱, 코드 포맷, 표 생성)은 작은/빠른 모델. 어려운 작업(가설 설계, 결과 해석, 검증)은 최상위 모델.
- **프록시 우선 원칙**: 비싼 실험 앞에는 항상 값싼 실험이 있어야 한다.
- 병렬화는 독립적인 것만. 의존관계가 있으면 순서대로.
- 재사용: 자주 쓰는 프롬프트(가설 형식화, 검증 감사, 실험 기록)를 템플릿/스킬로 고정.

## 7. 안티패턴 (하지 말 것)

| 안티패턴 | 왜 문제인가 | 대응 |
|---|---|---|
| 베이스라인 없이 시작 | 모든 후속 결과가 해석 불가 | GATE-B 강제 |
| seed 1개 비교 | 노이즈를 개선으로 오인 | 3 seed + 분산 기준선 |
| 한 실험에 여러 변경 | 원인 규명 불가 | 1실험 1변수 |
| 결과 보고 해석 만들기 | 사후 합리화 | 사전 등록(예상 결과 먼저 기록) |
| AI에게 검증까지 맡기기 | 자기 검증 통과율 왜곡 | Validator 분리 |
| 문헌 조사 → 데이터 분석 직렬 | 사이클 2배 | P1 병렬 |
| 프록시 결과를 최종 결론으로 | 스케일에서 뒤집힘 | GATE-P 승격 절차 |
| 테스트셋 반복 사용 | 다중 비교로 과적합 | val로 탐색, test는 최종 1회 |
| 스윕 최고값 vs 베이스라인 기본값 | 불공정 비교 | 동일 예산 튜닝 |
| raw 로그 전체를 프롬프트에 | 컨텍스트 붕괴, 비용 폭증 | 압축 계층 |
| rejected 목록 미관리 | AI가 같은 제안 반복 | rejected.md 주입 |
| AI 인용 그대로 신뢰 | 존재하지 않는 논문 | 인용 전수 검증 |
| 반증 조건 없는 가설 | 무한 튜닝 늪 | 가설 템플릿 강제 |

## 9. 논문 대비 이 워크플로우의 차별점

| | 논문1 | 논문2 | 논문3 | **본 워크플로우** |
|---|---|---|---|---|
| 대상 | 연구 활동 전반 | 계산생물학 | 정보 조사 | **딥러닝 모델 개발** |
| 속도 모델 | 미규정 | 분 단위 단일 루프 | 미규정 | **Fast/Slow 이원 루프** |
| 상태 관리 | 없음 | world state (메모리) | 메모리 계층 | **파일 기반 + 압축 계층 + tried/rejected** |
| 게이트 | 개념적 | 없음 | 품질 임계치 언급 | **GATE-B/P/V 수치 게이트** |
| 검증 | 이론 정합성 | critical reflection | validator 역할 | **Builder/Validator 강제 분리 + 다관점** |
| 재현성 | 미해결 과제로 지목 | 코드 공개 | 표준화 필요 지적 | **seed 정책·평가코드 동결·증거 링크 규격화** |

핵심 추가분은 세 가지다. **① Fast/Slow 이원 루프**로 딥러닝의 긴 학습 시간을 흡수한 것, **② 수치 기반 게이트(특히 seed 분산을 개선 판정의 기준선으로 삼은 것)**, **③ Builder와 Validator의 컨텍스트 분리**를 규범으로 못 박은 것.
